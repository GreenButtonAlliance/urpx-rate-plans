# Modeling gaps

What this corpus does not yet model, and why. Two different reasons, kept apart because they need different things to move.

[README](./README.md) describes what the corpus *does* contain, including the per-filing fidelity table. Each filing's `tariff.toml [extraction.notes]` records its own deferrals. This file is the corpus-wide view.

## Cannot be expressed in URPX v0.5.1

The tariff constructs the shipped SHACL shapes refuse. Each entry gives the upstream thread, what the shapes refuse, and where in the corpus it bites. These move when URPX does.

These are the tariff constructs this corpus cannot express in URPX v0.5.1. Each entry gives the upstream thread, what the shapes refuse, and where in the corpus it bites.

- [**urpx#10**](https://github.com/urpx-org/urpx/issues/10): `urpx:ProgramTypeValue` is a closed eight-value enumeration with no extension point, so a utility-minted category does not validate even when bridged to a shipped value with `skos:broader`, and `ProgramEnrollmentShape` is `sh:closed`, so no annotation can be hung on the enrollment either. Four kinds of program in this corpus have no value: senior citizen / disability (LADWP Lifeline, SCE Medical Baseline), deed-restricted affordable housing (SCE Deed-Restricted, SDG&E DRAH), critical peak pricing (SCE PRIME-CPP, SMUD CPP; price exposure without a curtailment obligation, so not `demandResponseProgram`), and supply arrangements (PG&E E-1's Direct Access and Transitional Bundled Service enrollments carry `urpx:programName` with no `urpx:programType`). The seven modifier filings for those programs model no `urpx:ProgramEnrollment` at all.
- [**urpx-org/urpx discussion #31**](https://github.com/urpx-org/urpx/discussions/31): `PlanElementsShape.hasProfileAlternatives` is `sh:maxCount 1` and a `RatePlanVersion` admits exactly one `PlanElements`, so a version reaches exactly one `ProfileAlternatives` container, and a container groups the mutually exclusive options of ONE dimension. A second independent dimension has nowhere to live, so two dimension groups can only be stated as their full cross-product. Note that the cap is on the container, not on references to its members: `PriceDefinition.referencesProfileAlternative` is unbounded, and `PriceDefinition.referencesProfileAlternatives` is `sh:maxCount 1`. A PriceDefinition can therefore name several alternatives from one dimension, which does not help across two. Bites PG&E E-1 2026-03-01, which needs income tier × baseline territory-code and so models a single baseline cell (Territory P, Code B) rather than the published 10 territories × 2 codes × 2 seasons; expansion is tracked at [urpx-rate-plans#18](https://github.com/grid-coordination/urpx-rate-plans/issues/18). PG&E E-TOU-C is unaffected because territory-code is its only dimension: its baseline-tier modifier ships all 40 cells as profile-scoped `urpx:ServiceBracket` nodes.
- [**urpx-org/urpx discussion #32**](https://github.com/urpx-org/urpx/discussions/32): `urpx:ServiceBracket` carries absolute `lowerBound` / `upperBound` only and `ServiceBracketShape` is `sh:closed`, so an additive baseline allowance cannot appear as data anywhere in the graph; the shift has to be precomputed into an absolute bound for every (territory, code, season) cell, including in a modifier overlay that supplies its own `ServiceTiers`. Blocks PG&E medical baseline Code M / Code S (+16.438 kWh/day) and SCE HPWH (+1.9 kWh/day summer, +2.6/3.0 kWh/day winter for HPWH-attesting TOU-D customers). Neither modifier is modeled here, which is the effect. The two filings that do carry baseline structure, PG&E E-1 (6 `urpx:ServiceBracket`) and the E-TOU-C baseline-tier modifier (120), can state absolute bounds only, so an additive allowance would have to be precomputed into every cell of both.
- [**urpx-org/urpx discussion #34**](https://github.com/urpx-org/urpx/discussions/34): `urpx:basedOnPrice` requires its target to be typed `urpx:Price` or `urpx:PriceSummary` in the same graph, so a filing cannot reference a price that is not determinable when it is written. Bites LADWP NEM and SMUD NEM1, which compensate exported energy at whichever base-rate energy charge the customer is on and therefore ship a placeholder `Price` of `unitPrice="0"`.
- [**urpx-org/urpx discussion #36**](https://github.com/urpx-org/urpx/discussions/36): a Standby Charge's on-site-generation exemption and conditional demand credit have no structured form. `DistributedEnergyResourceShape` is `sh:closed` over 12 properties with no operating mode, so a backup-only generator cannot be distinguished from one that offsets purchases; `enrollmentStatus` enumerates six lifecycle values, none meaning eligible but not enrolled; and `CalculationMethodShape` is `sh:closed` with no condition path, `urpx:hasConditionExpression` being restricted to `EligibilityRule`, `ApplicabilityRule`, `ApplicabilityGroup` and `ProfileAlternative`, which leaves free-text `calculationFormula` as the only route. Bites the Standby Charge sections of CPAU E-4, E-4 TOU, E-7 and E-7 TOU.
- [**urpx-org/urpx discussion #37**](https://github.com/urpx-org/urpx/discussions/37): `urpx:aggregationMethod` on a `urpx:CalculationMethod` states the operation, but nothing names the set it ranges over, and v0.5.1 has no site or account class (`urpx:AccountServiceAgreement` records that service account data lives in customer data rather than in URPX), so a sum of per-account monthly maximum demand cannot be scoped to the accounts at one site. Bites CPAU E-7 and E-7 TOU, which defer Section D.3 site aggregation to prose.
- [**urpx-org/urpx discussion #38**](https://github.com/urpx-org/urpx/discussions/38): an operand literal cannot carry a unit (`DatatypeOperandNodeShape` is `sh:closed`, and `urpx:unitOfMeasure` attaches only to a `MetricSpecification`), and URPX names no canonical baseline-allowance metric, so a percent-of-baseline threshold has to be stated as a dimensionless ratio over two producer-defined `MetricInput` references. Bites PG&E EV2, whose 800%-of-baseline annual usage cap is modeled as a comparison against a bare `800` with the percent semantics in `urpx:description` prose.

## Not yet modeled

Tariffs and modifiers that URPX can express and this corpus has not converted. These move when someone does the work.

Tracked in [Issues](https://github.com/grid-coordination/urpx-rate-plans/issues) and the local `bd` (beads) issue tracker. Highlights:

- SCE TOU-D HPWH (Heat Pump Water Heater) baseline-allocation modifier and PG&E Code M / Code S medical baseline modeling, both blocked on [urpx-org/urpx discussion #32](https://github.com/urpx-org/urpx/discussions/32) (additive baseline allowance vocabulary). Three CA IOUs hitting the same shape; the +1.9 / +2.6 / +3.0 kWh/day SCE HPWH extension structure documented in SCE Preliminary Statement Part H; URPX vocabulary path TBD.
- PG&E CARE/FERA modifiers: same shape as the SCE and SDG&E modifiers, which now carry both the line-item exemptions and the headline percentage discount, so the pattern to follow is established; deferred for utility-coverage breadth.
- SMUD EAPR income-tier usage discount: the program gives a 100 percent reduction in usage cost capped at $60, $32, $10 or $0 per month by Federal Poverty Level tier. URPX v0.5.1 can express a capped credit as marginal `urpx:ServiceBracket`s over a money-denominated `urpx:MetricInput`, with a -1.0 multiplier on the first bracket and 0.0 on the remainder, and that construction validates. What it cannot state is that a bracket bound of 60 means sixty dollars: `urpx:ServiceBracket` bounds carry no unit, and `DatatypeOperandNodeShape` is `sh:closed` with `urpx:unitOfMeasure` attaching only to a `MetricSpecification`. The $10/month fixed-charge discount is modeled exactly.
- LADWP REO (Renewable Energy Option): REAF dollar value not published in the tariff ordinance (formula only); needs source-discovery for an LADWP annual REA report before modeling. Tracked as a closed-deferred issue; re-file if the value is published.
- Smaller-utility coverage (Imperial Irrigation District, City of Anaheim, Modesto Irrigation District, Riverside, Glendale, etc.): each adds ~50K–150K residential customers and broadens statewide coverage.
